# Hosted project containment qualification

The web shard also runs one fixed-public CPU request on a fresh Unix user's real
default-home worker. It binds that worker to loopback before authorizing the public
controller key, pins its TLS fingerprint, and explicitly selects it with `--on`.
Origin-project input bytes, output bytes and canonical run/log rows are checked
again after the exact remote processes retire. The remote invocation must contain
neither local private storage nor the origin mount path/proof token. Its ordinary
external working copy is preserved. All inspection output stays in RAM; no scan
exclusion, alternate Cozy home, rental, raw log or payload artifact is added.

This fixture is prepared for an isolated Linux hosted runner. Do not dispatch it until the
coordinator supplies the composed candidate and explicitly marks it ready. It reads no real
user's home on the development workstation and starts no browser.

The fixture uses the installed candidate CLI, its real Calcifer (its own child) and the real
encrypted provider. Cozy owns no browser (cl-1067): any browser of this account opens the page,
so what a locked project must guarantee rests on the responses and the page. The page's own
storage after a lock is `web-vault`'s; what's typed as a lock begins is `web-restart`'s.

## Access rule under test

There are no browser sessions (design/calcifer-access.md). Every request needs a loopback
peer, a `Host` of the listener and, if sent, an `Origin` of that Host. `/v1`, media and the dev
page also need the peer's Unix account to be Calcifer's; then `Sec-Fetch-Site: same-origin`
(the page), or, from a non-browser, the lock record's bearer. A navigation's `none` opens only
the page's files.

## Required real execution

1. Refuse outside a fresh hosted Linux test-Hub runner; pin and hash the installed candidate.
   Open two born-encrypted project folders with credentials supplied on stdin. Capture CLI
   output in RAM. Write source, names, prompts, image metadata and all fixture-owned private
   outputs only inside their unlocked project views.
2. Request project files, pictures, thumbnails and ranges as the page does (same-origin, no
   bearer). Assert no-store on 200, 206 and conditional answers, and that the page's capability
   names `user:<euid>` and this Calcifer's birth. On a project route and a media route, refuse a
   fresh Unix account the check makes and removes, even with the bearer (`other_user`),
   `Sec-Fetch-Site` cross-site/same-site/`none` (`not_own_page`), a foreign Origin
   (`origin_not_allowed`), and no bearer or browser headers or a WebSocket upgrade there
   (`unauthenticated`).
3. Lock A through the CLI; its view is gone.
4. SIGKILL the fixture's Calcifer and start the next one; cold-restart it with `down`. Observe
   the old bearer refused each time.
5. Run read-only scans of the exact home, global DB+WAL/SHM, service/log captures and
   configured temporary/cache locations. Scan raw bytes, filenames and SQLite logical values;
   decode supported gzip/zlib bodies. B's still-unlocked view is excluded only by its exact
   provider root and is scanned after B locks.
   Paul's invariant (cl-984): once a project is locked, nothing of it stays outside its folder
   except that folder's path. Its id and name (a unique folder name) are searched for everywhere
   outside the folder, with the path itself cut out first. Its prompt, input digest, outputs, runs
   and logs are searched for everywhere, its own encrypted folder included.

On an unexpected CLI exit the receipt keeps only allowlisted code/kind/cause booleans,
exit status and hashes. No raw CLI output, path, project reference or credential is evidence.

Receipts retain fixed case names, checks, counts, hashes, status codes and timing boundaries.
They never retain raw response/error bodies, SQL values, canaries or project-derived
filenames. On failure, write sanitized counts/hashes and leave the owned synthetic project
folders intact for coordinator-owned investigation. Never collect mixed raw daemon logs into
the uploaded output directory.

## Runtime entry and artifact limits

`uv run --no-project e2e/cli/containment/run.py --ready-file READY.json --out OUT` refuses
unless this is a hosted Linux runner, its isolated Hub is independently verified, the default
installed Calcifer is stopped, and the coordinator's ready file contains
`{"ready":true,"sha256":"<exact installed candidate SHA-256>"}`. That ready file is supplied by
the coordinator after composition, never generated by this fixture.

The scanner reads every regular file and filename under the declared roots. Files up to
64 MiB additionally receive SQLite-in-RAM, ZIP, gzip/zlib, LevelDB/Snappy and image decoding;
larger files are counted as `large_raw_only`. The receipt preserves that limit explicitly.
The fixed random black/white tile pattern recognizes a re-encoded private image/thumbnail
without requiring the original PNG metadata to survive. Missing decoders, unreadable files,
or undecodable recognized formats fail the case. The final receipt is the only generated
outside evidence file and contains fixed case codes plus counts, hashes and statuses.

## Actual managed execution storage

`native_execution: true` invokes a real weightless function through the installed CLI,
worker and Runtime. It verifies project-owned source, environment, HOME, cache, temporary
files, output bytes and history retained across lock and cold restart. It checks Cozy's
requested core limit is zero; it never changes the host's kernel core handler.

This fixture does not claim an OS sandbox. Deliberate external writes made by custom
Python and exports are outside the automatic-storage guarantee. Older failed sandbox
receipts remain failures and are not relabeled as managed-storage passes.

## Optional real development case

`development_web: true` in the coordinator's ready file additionally requires a hosted runner
with pnpm and the checkout's web dependencies installed. The fixture owns one Vite process
and sets `[calcifer].development_web`; a first Calcifer, before any project, must still serve
its embedded page and no `/__cozy_hmr` upgrade. Only then does it add top-level `dev = true`
for its foreground Calcifer. This account's upgrade with the exact Origin gets 101; the fresh
account's gets 403 `other_user`. The page Calcifer serves carries a nonce CSP naming its HMR
socket and no-store, and Vite itself answers every `/v1` path with 404
`development_api_in_calcifer`. A page's hot update through Calcifer is `web-access`'s.
