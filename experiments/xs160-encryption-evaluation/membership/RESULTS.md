**Verdict:** OpenMLS 0.9.2 is a viable evaluated building block for an epoch-based group-key channel. This binary actually created groups, joined members, encrypted content-key messages, restored local state, rejected stale history, resolved a membership-commit race with an explicitly selected winner, and revoked future access. It does not supply Cozy's durable archive, account recovery, project permissions, or offline delivery service.

Evaluation date: 2026-11-09. All operations ran locally in one standalone Rust binary with genuine library crypto; no paid services, account, production integration, mock crypto, or benchmark. The fixture's JSON object/key labels are deliberately synthetic and are not a proposed production wire schema.

The pinned [manifest](Cargo.toml), [lockfile](Cargo.lock), [source](src/main.rs), and exact [machine-readable results](results.json) are in this directory. Official package documentation lists [OpenMLS 0.9.2](https://docs.rs/crate/openmls/0.9.2), released 2026-10-22. Matching `openmls_rust_crypto`, `openmls_basic_credential`, `openmls_memory_storage`, and `openmls_traits` are all 0.6.0. `tls_codec` is 0.5.0. The separate synthetic archive uses `aes-gcm` 0.10.3 / AES-256-GCM; `serde` resolved to 1.0.229 and `serde_json` to 1.0.154. Cargo.lock pins all transitive packages.

**Observed behavior**

The MLS suite was `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`. The main groups explicitly used `PastEpochDeletionPolicy::MaxEpochs(0)`. The separate retained-state Bob used `MaxEpochs(2)` for one delayed-message comparison.

| Case | Actual state and output |
| --- | --- |
| Create / add / join | Alice created epoch 0 and added Bob. Bob joined with his Welcome and private KeyPackage state at epoch 1. Both views contained Alice/Bob and their epoch authenticators matched. A stranger trying the same Welcome failed with `NoMatchingKeyPackage`. |
| Alice → Bob content key | A genuine MLS `PrivateMessage` delivered a random 32-byte object key inside synthetic JSON. Bob's processed credential identified Alice, and AES-256-GCM decrypted the separate 64-byte object. The final randomized fixture's MLS message was 306 bytes. Replay failed with `ValidationError(UnableToDecrypt(SecretTreeError(SecretReuseError)))`; a bit-flipped message failed with `ValidationError(UnableToDecrypt(AeadError))`. |
| Persist / reload | Bob's 12 storage entries were serialized, AEAD wrapped, and written to `encrypted-local-state.json` (96,199 bytes in the final run). The original Bob provider, group, and signer were dropped. A fresh provider read/decrypted the file, restored its storage, loaded the signer with `SignatureKeyPair::read`, loaded the group with `MlsGroup::load`, matched Alice's epoch authenticator, and decrypted a newly sent message at epoch 1. |
| Add Carol / history | Carol joined at epoch 2 and could not decrypt the saved epoch-1 MLS key message: `ValidationError(UnableToDecrypt(SecretTreeError(TooDistantInThePast)))`. Carol could decrypt the old object only after Alice explicitly re-sent its object key in epoch 2. This is an explicit application grant of historical data. |
| Delayed offline message | Bob with `MaxEpochs(0)` could not decrypt an unread epoch-1 message after merging epoch 2: the same `TooDistantInThePast` error. A copy of Bob's actual epoch-1 state configured to retain two past epochs before the transition successfully decrypted that same delayed message after merging epoch 2. This only tests a one-epoch delay, not unlimited offline catch-up. |
| Concurrent membership commits | At epoch 2 Alice generated add-Dave while Bob independently generated remove-Carol. Both had real pending commits. The fixture chose Alice's commit first; Bob merged it even with his own pending commit, and his losing pending commit was cleared. Alice/Bob/Carol/Dave agreed at epoch 3. Trying Bob's old commit then failed with `ValidationError(WrongEpoch)`. Bob recreated his removal at epoch 3; survivors agreed at epoch 4 and Carol became inactive. |
| Remove Bob | Alice removed Bob, leaving Alice/Dave at epoch 5. Dave decrypted a new random content key. Bob who processed removal failed with `GroupStateError(UseAfterEviction)`. A separately loaded Bob deliberately left at epoch 4 without seeing the removal failed with `ValidationError(WrongEpoch)`. Bob's already obtained revision-1 object key still decrypted that old object. |
| Archive boundary | An empty fresh provider could not load this group (`None`). A separately AEAD-wrapped object-key envelope read from disk, plus an independently available random recovery wrapping key, decrypted the encrypted object also read from disk. A wrong recovery key failed AEAD authentication (`Error`). This did not reconstruct the MLS group. |

The storage adapter is the real provider's [MemoryStorage](https://docs.rs/openmls_memory_storage/0.6.0/openmls_memory_storage/struct.MemoryStorage.html), whose public byte map makes this narrow reload experiment possible. [OpenMlsRustCrypto](https://docs.rs/openmls_rust_crypto/0.6.0/openmls_rust_crypto/struct.OpenMlsRustCrypto.html) uses it by default. The local-state encryption wrapping key remained in process across the drop/reload. This proves a serialized state round trip, not a process restart, crash-atomic persistence, rollback protection, cross-version migration, or a deployable storage adapter.

**Consequences for xs160**

Membership operations are linear epoch transitions. The executable deliberately simulated a sequencer decision; it did not obtain automatic conflict merging from MLS. A real service must arrange a common accepted commit history, couple Welcome delivery to the winning commit, and let a rejected client recreate its membership operation against the accepted epoch. [RFC 9750, delivery](https://www.rfc-editor.org/rfc/rfc9750.html#section-5.2) also describes alternate eventual-consistency strategies; those were not evaluated. OpenMLS's own [forward-secrecy guidance](https://book.openmls.tech/forward_secrecy.html) requires waiting for delivery acceptance before merging one's pending commit and explains per-message key disposal.

MLS identity and application authority remain distinct. The fixture used self-asserted BasicCredential strings with generated signing keys, not a real authentication service. It verified message authenticity to the expected fixture key, not a person's account, a worker lease, or a trusted device enrollment. Bob was able to remove Carol because no application policy rejected that commit. MLS does not provide Cozy's typed output-only-producer versus editor rules, constrain document operations by role, or decide which historical object keys a member may receive. A member receiving a shared content-key stream can read that stream. [RFC 9750, access control](https://www.rfc-editor.org/rfc/rfc9750.html#section-6.4) places such policy in the application.

Long-lived project history needs an explicit recoverable key/archive mechanism. Retaining some old epoch secrets helps delayed delivery but is not a history grant for a new device/member, and consuming MLS messages is intentionally different from durable object storage. The encrypted `synthetic-archival-envelope.json` and `synthetic-encrypted-object.json` illustrate ordinary AEAD wrapping of a durable object's key. The recovery key was generated independently and kept in memory, never derived from the account or MLS identity and never provisioned to an external backup system. The resulting files alone are intentionally insufficient after the evaluation process exits. No final archive schema or new cryptographic protocol was invented here. [RFC 9750, state loss and multiple devices](https://www.rfc-editor.org/rfc/rfc9750.html#section-6.6) likewise separates rejoining from restored history.

Untested: real account/device authentication and revocation; typed app-operation authorization; worker delegation; actual network delivery, offline queues, long absences, dropped commits, and malicious forks; many-device users; secure recovery-key custody; full project reconstruction after all devices and live MLS state are gone; archive retention and revocation policy; secure atomic durable storage; interoperability with another MLS implementation; upgrades; broad cryptographic audit; scale and performance. Those require application design and integration evidence beyond this standalone library evaluation.
