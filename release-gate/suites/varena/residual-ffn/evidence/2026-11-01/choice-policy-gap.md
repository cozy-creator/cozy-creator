# The complete Tail exposes a phase-plan gap

Full matched runs25112/25151 prove1500 actual native Tail executions. The candidate
chooses27280 rows752 times and54562 rows543 times, with measured backing3,363,831,808 B
and6,687,817,728 B respectively; six whole109123-row choices reach13,337,886,720 B.
The control's legacy fitted path mostly uses3307 rows1166 times and1679 rows332 times.

The complete native menu is truthful about the operation's buffers. It still has
`preferred=choices[0][0]` in Runtime `native_residual_ffn.py`: whole rows, and choices
are ordered largest to smallest. Native `working/split.rs::headroom` subtracts the
currently owned working and weight pages from the cap; `fits` considers reusable
current working blocks. Neither receives all declared phase weight requirements or
an efficient streaming-kernel preference for this compound operation.

Consequently a large choice may fit beside currently resident weights while reducing
room for the next declared model weights. In this pair, rest-loop measured working
backing rises17,328,766,976→20,015,218,688 B, transformer fills1038→1081, and recorded
store bytes rise17,455,363,584 B (+3.876%). Denoise is+0.889%. The counters and source
support a phase-planning deficiency; the single pair does not isolate every driver's
cost or establish an optimal fixed chunk.

The required next seam is an actual committed phase plan: choose a working layout
that fits beside the declared phase weights, then use a provider-supported efficient
chunk when streaming is unavoidable. Unknown layouts/legacy adaptive paths remain
demand-only. Do not insert the previous fingerprint as a guessed current key, restore
old Python window formulas, or hardcode~3k rows based on this one model run. The same
plan must qualify measured working reuse and optional prefetch before execution.
Tail and upcoming complete _Heads choices must be frozen consistently in that plan.
