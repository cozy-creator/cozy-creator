The open RC's TensorFS is its own minor's dev line: rc/0.27.0's crates say `0.27.0-dev` and its builds `0.27.0.dev<n>+g<sha8>`, n the commit's first-parent count, as the Runtime's are (`crates/tensorfs-py/scripts/dev-version.sh` stamps rc-dev's, dev-build's and the e2e's). The Runtime can floor on a build (`tensorfs>=0.27.0.dev3298`), so an RC Runtime is refused beside a TensorFS that lacks what it calls (gate 44238862903: `Device.region() takes 3 positional arguments but 4 were given` on the Hub's 0.26.0).

A lock on an RC Runtime build takes the RC's TensorFS build beside it, by URL for Linux x86_64 (`floor::rc_tensorfs_wheel`); rc-dev keeps a TensorFS build the RC's Runtime lock or a type check pins. The release gate refuses at $0 a Runtime whose range doesn't admit the TensorFS its machine would run, takes the RC's TensorFS for an RC Runtime given alone, and `-f rent=false` runs that check by itself (`release-gate/resolve.py`, `gate.sh --preflight`).
